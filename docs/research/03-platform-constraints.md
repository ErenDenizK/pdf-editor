**Deployment via GitHub Actions** (Vite docs' workflow): `actions/checkout` → build → `actions/configure-pages@v5` (optional) → `actions/upload-pages-artifact@v3` → `actions/deploy-pages@v4`. The deploy job needs `permissions: pages: write, id-token: write` (+ `contents: read`), `environment: github-pages`, and `needs: build`. `deploy-pages@v4` is mandatory since the artifacts-v4 cutover (Jan 30 2025). Add `concurrency: { group: pages, cancel-in-progress: false }`. Sources: [github.blog changelog 2024-12-05](https://github.blog/changelog/2024-12-05-deprecation-notice-github-pages-actions-to-require-artifacts-actions-v4-on-github-com/), [actions/deploy-pages](https://github.com/actions/deploy-pages).

**SPA routing:** (a) `404.html` redirect trick ([rafgraph/spa-github-pages](https://github.com/rafgraph/spa-github-pages)): 404.html rewrites `/a/b?x=1` → `/?/a/b&x=1`, index.html restores it with `history.replaceState`. For project sites set `pathSegmentsToKeep = 1`. Caveats: an extra redirect on cold loads, real 404 status is returned first, Google stopped following 404-page redirects (~2019) so deep links aren't indexed. (b) Hash routing: zero infrastructure, always works on refresh, ugly URLs. **Recommendation for a PDF editor:** you barely need URL routes; use hash routing (or no router) and skip the 404 hack. Also deploy a plain `404.html` so a missing asset doesn't return `index.html`.

## 2. WASM threading, SharedArrayBuffer (SAB) and memory

**Rules.** SAB and wasm threads require a cross-origin-isolated document: `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp|credentialless`. BCD: SAB re-enabled Chrome 68 (with COI from 92), Firefox 79, Safari 15.2 (all gated behind COI). COEP `credentialless`: Chrome 96, Firefox 119, **Safari: not supported** (`require-corp` only). Sources: [BCD SharedArrayBuffer.json](https://github.com/mdn/browser-compat-data/blob/main/javascript/builtins/SharedArrayBuffer.json), [BCD COEP header](https://github.com/mdn/browser-compat-data/blob/main/http/headers/Cross-Origin-Embedder-Policy.json).

**GitHub Pages can't set those headers → the only workaround is a service worker that synthesizes them.**

### `coi-serviceworker` (gzuidhof) — how it works and caveats
- Repo: https://github.com/gzuidhof/coi-serviceworker (MIT; npm `coi-serviceworker@0.1.7`, published 2023-07-09; no GitHub Releases, repo still gets PRs). Based on stefnotch's blog idea; the technique is also endorsed by Chrome DevRel (Thomas Steiner, [2025-03-08 post](https://blog.tomayac.com/2025/03/08/setting-coop-coep-headers-on-static-hosting-like-github-pages/)).
- Mechanism (read from `coi-serviceworker.js`): the same file acts as both the page script and the SW. On first load, if `window.crossOriginIsolated === false`, it registers itself (`register(document.currentScript.src)`) and then **reloads the page once** (`sessionStorage.coiReloadedBySelf`) so the controlled navigation gets `COOP: same-origin` + `COEP: credentialless` (default) injected into every same-origin response via `respondWith`. If `crossOriginIsolated` is still false after reload, `coepDegrade` triggers a second reload with `require-corp`. Configurable via `window.coi = { shouldRegister, shouldDeregister, coepCredentialless, coepDegrade, doReload, quiet }`.
- Requirements: must be served from your own origin (not a CDN), on HTTPS or localhost, and loaded as a classic script before anything that needs SAB.
- **First-load reload:** unavoidable (one, sometimes two, reloads on first visit per session). Provide `doReload` to show a "preparing…" screen; the user's dropped file is lost if they drop before the reload, so gate the drop zone on `crossOriginIsolated`.
- **Safari/iOS:** WebKit honors SW-injected COOP/COEP (PR #13 "Allow Safari/WebKit to have SharedArrayBuffer too", merged) but only `require-corp`, so the credentialless→require-corp degrade path (issues #20, PRs #21/#25) is what makes Safari work; that means **every cross-origin resource you load must send CORP/CORS headers** (fonts, CDN scripts, images), or it fails under `require-corp`. Safari's "Private Browsing" and iOS memory pressure also evict SWs more aggressively; treat Safari as best-effort.
- **Firefox:** service workers are unavailable in Private Browsing (`navigator.serviceWorker` undefined; [Bugzilla 1320796](https://bugzilla.mozilla.org/show_bug.cgi?id=1320796)); community thread reports intermittent Firefox reliability. The script handles missing SW by giving up (no loop).
- **Embedded contexts** (iframes on other sites, itch.io-style portals) break: issue #17.
- **Production use:** Godot web exports (community plugin [nisovin/godot-coi-serviceworker](https://github.com/nisovin/godot-coi-serviceworker), Godot Asset Library), whisper.cpp browser demos (vendored `coi-serviceworker.js` in Hugging Face Spaces), Pyodide/pygame demos on itch.io. It is a well-trodden hack but still a hack: you cannot make a *guarantee* that the app is isolated, so design for the non-isolated path.

### Do the PDF engines actually need threads? No.
- **pdf.js** (`pdfjs-dist@6.3.289`, 2026-08-29, Apache-2.0, Node ≥ 22.13): pure JS core running in a dedicated **Web Worker via postMessage**; no SAB. Since v5 the JPX (OpenJPEG), JBIG2 (PDFium's decoder) and ICC decoders are single-threaded **WASM side files** that must be served and located with the `wasmUrl` option (otherwise you get `nullopenjpeg.wasm` 404s). Sources: [pdf.js releases](https://github.com/mozilla/pdf.js/releases), [discussion #20585](https://github.com/mozilla/pdf.js/discussions/20585).
- **PDFium wasm via EmbedPDF** (`@embedpdf/pdfium@2.15.1` and `@embedpdf/engines@2.15.1`, 2026-09-16, MIT; core Apache-2.0): its build script `packages/engine/runtime/build/compile.esm.sh` links with `-sMODULARIZE=1 -sWASM=1 -sALLOW_MEMORY_GROWTH=1 -sALLOW_TABLE_GROWTH=1 -sEXPORT_ES6=1 -sENVIRONMENT=web,worker` — **no `-pthread`**, i.e. single-threaded, no SAB needed. PDFium itself "makes no guarantees about thread safety" (pdfium mailing list), so multithreading a single engine instance is pointless anyway. Source: [compile.esm.sh](https://github.com/embedpdf/embed-pdf-viewer/blob/main/packages/engine/runtime/build/compile.esm.sh).
- **MuPDF.js** (`mupdf@1.28.1`, 2026-09-06, **AGPL-3.0-or-later or commercial**): `platform/wasm/tools/build.sh` links with `emcc -Os -fwasm-exceptions -sMODULARIZE=1 -sEXPORT_ES6=1 -sALLOW_MEMORY_GROWTH=1 -sTEXTDECODER=2 -sFILESYSTEM=0` — **no `-pthread`**, single-threaded; docs ship a Web Worker example (`examples/simple-viewer`). Objects need manual `.destroy()` (WASM heap is not GC'd). License is the deal-breaker for a non-AGPL app. Source: [build.sh](https://github.com/ArtifexSoftware/mupdf/blob/master/platform/wasm/tools/build.sh).
- Also: Godot 4.3+ ships a no-threads web export precisely so games work without COI; the same pattern applies here.

**What Web Worker + single-threaded WASM gives you:** the UI thread never blocks (parsing/rendering/saving happens off-thread), you can run **N independent worker instances** (one per document, or a small pool) to get real parallelism across documents without SAB, transfer `ArrayBuffer`s/`ImageBitmap`s zero-copy via `postMessage` transfer lists, and render into `OffscreenCanvas` inside the worker. What you lose vs. pthreads: intra-document parallel rendering and shared heaps — irrelevant for PDFium/MuPDF (not thread-safe) and for pdf.js (JS). **Recommendation: design for single-threaded WASM in workers; make COI (coi-serviceworker) an optional progressive enhancement only if you later add a threaded component (e.g. Rust + `wasm-bindgen-rayon`, which additionally requires nightly Rust `-Z build-std` for `atomics`, see [RReverser/wasm-bindgen-rayon](https://github.com/RReverser/wasm-bindgen-rayon)).**

### Memory limits
- **wasm32 heap:** hard ceiling 4 GiB. Emscripten `MAXIMUM_MEMORY` defaults to **2 GiB** (from `src/settings.js`: pointers must be unsigned above 2 GB → larger code; set `-sMAXIMUM_MEMORY=4GB` to raise). Both engines above use `ALLOW_MEMORY_GROWTH` without `MAXIMUM_MEMORY` → **2 GiB max heap per engine instance**. Growth reallocates and invalidates `HEAPU8` views (fine unless you cache views); with pthreads growth also makes JS-side heap access slow — another reason to stay single-threaded. Sources: [emscripten settings.js](https://github.com/emscripten-core/emscripten/blob/main/src/settings.js), [pthreads.rst](https://github.com/emscripten-core/emscripten/blob/main/site/source/docs/porting/pthreads.rst), [V8 "Up to 4GB of memory in WebAssembly"](https://v8.dev/blog/4gb-wasm-memory), Firefox large memories from 89 ([Bugzilla 1703505](https://bugzilla.mozilla.org/show_bug.cgi?id=1703505)).
- **Memory64 (wasm64):** BCD: Chrome 133, Firefox 134, **Safari: preview only** (Safari Technology Preview 251/252 added Memory64 + multi-memory; not in a stable Safari release per BCD `main` as of Sept 2026). Emscripten: `-sMEMORY64` deprecated in favor of `-m64`/`--target=wasm64`; ~10% throughput cost reported; browsers cap wasm64 at ~16 GB. Only worth it if you need > 4 GB — a PDF editor should stream/page instead. Sources: [BCD webassembly/memory64.json](https://github.com/mdn/browser-compat-data/blob/main/webassembly/memory64.json), [webkit STP 251 notes](https://webkit.org/blog/18194/release-notes-for-safari-technology-preview-251/).
- **Practical guidance for large PDFs:** never load the whole file into the WASM heap *and* a JS copy; hand the engine the `ArrayBuffer` once (transfer it), keep page renders as `ImageBitmap`s, cap concurrent render jobs, and put scratch data in OPFS (section 3). Budget ~1.5 GB per worker before the 2 GiB ceiling bites; recycle workers per document.

## 3. Handling large files in the browser

### Support matrix (BCD `main`, read 2026-09-26)

Sources: [Window.json](https://github.com/mdn/browser-compat-data/blob/main/api/Window.json), [FileSystemFileHandle.json](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemFileHandle.json), [FileSystemWritableFileStream.json](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemWritableFileStream.json), [StorageManager.json](https://github.com/mdn/browser-compat-data/blob/main/api/StorageManager.json), [DataTransferItem.json](https://github.com/mdn/browser-compat-data/blob/main/api/DataTransferItem.json), [Worker.json](https://github.com/mdn/browser-compat-data/blob/main/api/Worker.json), [Firefox 147 release notes](https://www.firefox.com/en-US/firefox/147.0/releasenotes/).

### Strategy
- **Open:** try `showOpenFilePicker({multiple:true, types:[{accept:{'application/pdf':['.pdf']}}]})`; fall back to `<input type=file multiple accept=".pdf,application/pdf">`. Drag-and-drop: three-tier per `DataTransferItem` — `getAsFileSystemHandle()` → `webkitGetAsEntry()` (recursive directory walk; `readEntries` returns ≤100 entries per call, loop it) → `getAsFile()`. Handles let you **save back in place** (Chromium only, permission prompt).
- **Save:** Chromium — `showSaveFilePicker()` → `createWritable()` → stream chunks from the worker (pipe a `ReadableStream`), no giant Blob. Firefox/Safari — build the output in OPFS via `createSyncAccessHandle` in a worker, then `getFile()` → `URL.createObjectURL` → `<a download>` click (needs user activation in Safari; revoke the URL afterwards). Helper libs: [`browser-fs-access@0.38.0`](https://github.com/GoogleChromeLabs/browser-fs-access) (ponyfill with `<input>`/`<a download>` fallbacks; GoogleChromeLabs), [`native-file-system-adapter@3.0.1`](https://github.com/jimmywarting/native-file-system-adapter) (2024). **`StreamSaver.js@2.0.6`** is from 2022, relies on a MITM service worker page + `Content-Disposition` trick and the author himself calls it a "last resort" — avoid; OPFS + `<a download>` covers the same need today.
- **Scratch storage:** OPFS is ideal for decompressed page caches/undo snapshots/large intermediates: sync, fast, quota is a large fraction of disk (WebKit ~60%; Chrome/Firefox similar "best-effort" quota), evictable if the origin isn't persistent — request `navigator.storage.persist()` and handle `QuotaExceededError`. Unavailable in Safari Private Browsing. Sources: [MDN File System API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API), [RxDB OPFS notes](https://rxdb.info/rx-storage-opfs.html).
- **Memory ceilings (engine source, 64-bit):** V8 `JSArrayBuffer::kMaxByteLength` = `kMaxSafeBufferSizeForSandbox` = **32 GiB − 1** when the V8 sandbox is on (Chrome), else 2^53 ([js-array-buffer.h](https://github.com/v8/v8/blob/main/src/objects/js-array-buffer.h), [v8-internal.h](https://github.com/v8/v8/blob/main/include/v8-internal.h)); SpiderMonkey `ByteLengthLimit` = **16 GB** on 64-bit ([ArrayBufferObject.h](https://github.com/mozilla-firefox/firefox/blob/main/js/src/vm/ArrayBufferObject.h)); JavaScriptCore `MAX_ARRAY_BUFFER_SIZE` = **2^34 = 16 GiB** with `USE(LARGE_TYPED_ARRAYS)`, 2 GiB otherwise ([PageCount.h](https://github.com/WebKit/WebKit/blob/main/Source/JavaScriptCore/runtime/PageCount.h)). In practice allocation fails far earlier from per-tab memory pressure (Chromium bug ["Large ArrayBuffers are very unstable"](https://issues.chromium.org/issues/41082096)), Chrome's in-memory Blob store is ~500 MiB before spilling to disk, and the wasm heap is 2–4 GiB. **Treat ~1 GB per document as the design ceiling; above that, stream.**
- Multi-file: `input[multiple]`, `webkitdirectory` (Chromium/Firefox/Safari desktop), and `File.webkitRelativePath` for folder structure. Mobile Safari has no directory pickers.

## 4. Offline / PWA

- **Toolchain:** [`vite-plugin-pwa@1.3.0`](https://github.com/vite-pwa/vite-plugin-pwa) (2026-05-05) peers on `vite ^3–^8` and `workbox-build/window ^7.4.1` ([`workbox-build@7.4.1`](https://github.com/GoogleChrome/workbox), 2026-05-04; Workbox is maintained by Chrome's Aurora team but slowly). vite-pwa announced (issue #933, 2026-05-16) a modular `@vite-pwa/core` with a lean Workbox fork and a `buildSW` strategy bundling the SW natively with Vite 8/Rolldown, with dual ESM/classic SW output; `vite-plugin-pwa` will go maintenance-only — **use vite-plugin-pwa now, plan to migrate** ([issue #933](https://github.com/vite-pwa/vite-plugin-pwa/issues/933)).
- **Large WASM assets:** Workbox `maximumFileSizeToCacheInBytes` defaults to **2 MiB** and vite-plugin-pwa ≥ 0.20.2 *fails the build* if any precache entry exceeds it. Raise it (e.g. 20–40 MiB) or, better, **exclude multi-MB `.wasm` from precache and use `runtimeCaching` with `CacheFirst` + `ExpirationPlugin`** so first paint doesn't wait for a 10–20 MB engine download; content-hashed filenames make this safe. Keep total precache ≪ the 1 GB site cap. Watch Safari's cache eviction of inactive sites (7-day ITP rule for non-installed web apps).
- **Update strategy:** `registerType: 'prompt'` (show "update available" toast; a PDF editor must never reload under the user's feet) rather than `autoUpdate`; `skipWaiting` only on user confirmation; check for updates on focus. GitHub Pages' 10-minute `max-age` on `sw.js` means updates propagate within ~10 min; SW byte-compare update checks ignore HTTP cache >24 h anyway.
- **Installability UX (desktop):** Chrome/Edge show an omnibox install icon and fire `beforeinstallprompt` (custom "Install" button); Safari 17+ macOS: File ▸ Add to Dock (no prompt event); **Firefox desktop: no PWA install** (only bookmarks). Manifest needs `display: standalone`, icons (192/512 + maskable), `id`, `start_url`, `scope`; optionally `file_handlers` (Chromium: register as a handler for `.pdf` so installed app opens PDFs via `launchQueue`). Sources: [MDN Making PWAs installable](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable), [openpwa desktop install](https://openpwa.net/reference/installation/desktop-install/).
- **GitHub Pages project-site gotchas:** SW default scope is its own directory, so with `base: '/repo/'` the SW at `/repo/sw.js` scopes to `/repo/` (correct), but manifest `scope`, `start_url`, `id`, `navigateFallback`, and `workbox.navigateFallbackDenylist` must all be prefixed; vite-plugin-pwa derives these from Vite's `base` but several reports ([#263](https://github.com/vite-pwa/vite-plugin-pwa/issues/263), [#4](https://github.com/vite-pwa/vite-plugin-pwa/issues/4)) show hardcoded root paths breaking. Two project sites under the same `<owner>.github.io` origin share storage/quota and can clash on SW scopes if one uses `/` — a custom domain avoids that. Also: `navigateFallback` + the 404.html trick conflict; pick one.

## 5. Frontend stack recommendation (heavy canvas/document editor)

### Framework (versions as of 2026-09-26)
| | Version | Reactivity | Fit for thumbnail grids + canvas + workers |
|---|---|---|---|
| **React** | 19.3.0 (2026-09-09) | VDOM + React Compiler auto-memo | Largest ecosystem (dnd-kit/react, TanStack Virtual, Zustand/Jotai, EmbedPDF React bindings). Fine-grained enough with compiler + external stores; canvas work lives outside React anyway. |
| **Svelte 5** | 5.57.1 (2026-09-18) | runes / signals, compiled | Best raw update latency of the four in benchmarks (≈3× React INP on high-frequency updates); good `@tanstack/svelte-virtual`, `@dnd-kit/svelte 0.5`; smaller ecosystem for PDF SDKs. |
| **SolidJS** | 1.9.15 stable; 2.0.0-rc.9 (2026-09-18) | signals | Fastest fine-grained model; 2.0 (first-class async, new Rust/OXC compiler) is at RC — churn risk right now. |
| **Preact** | 10.29.8; 11.0.0-rc.2 (2026-09-08) | VDOM + `@preact/signals 2.11` | Tiny; React-compat layer covers most libs; 11 still RC. |

**Recommendation:** React 19 with the React Compiler *if* you want the EmbedPDF React bindings, `@dnd-kit/react`, and hiring familiarity; **Svelte 5 if you prefer performance-by-default and are happy with vanilla/headless libs** (EmbedPDF is framework-agnostic and ships Svelte bindings too). Either way keep the hot path (page rendering, pan/zoom, selection overlays) in plain canvas/`OffscreenCanvas` code driven by a store, not by component re-renders. Avoid Solid 2.0 RC/Preact 11 RC for a new production app until they ship stable.

### State management
- **Zustand 5.0.15** (module store, middleware; undo/redo via `zundo@2.3.0` or a custom command stack) — simplest default; store document models outside React and subscribe with selectors.
- **Jotai 3.0.0** (2026-09-08, ESM-only, drops `atomFamily`/`loadable`, React ≥ 18): atomic granularity suits per-page state (thumbnail, rotation, selection) with minimal re-renders; `jotai-history` for undo.
- **Valtio 2.3.2** proxy state; **XState 5.33.2 / `@xstate/store 4.2.3`** for explicit editor modes (idle → selecting → dragging → saving) and worker lifecycles — worth it for the tool-mode state machine only.
- Use **immutable command objects for undo/redo** (page reorder/rotate/delete/insert across documents) independent of the UI library; the engine only sees commands.

### Virtualization, DnD, worker RPC
- **`@tanstack/react-virtual 3.14.13` / `@tanstack/virtual-core 3.17.11`** (2026-09-14): grid ("lanes") virtualization for thumbnails; render placeholders and request thumbnails from the worker only for visible ± overscan rows; cache as `ImageBitmap`.
- **Drag-and-drop for reordering pages across documents:**
  - `@dnd-kit/core 6.3.1` (last release 2024-12-05) is stable but effectively frozen; docs repo archived 2026-02-21; roadmap questions unanswered ([discussion #1842](https://github.com/clauderic/dnd-kit/discussions/1842)). The rewrite `@dnd-kit/react`/`dom` is **0.5.0** (2026-06-11, pre-1.0, adapters for React/Vue/Svelte/Solid). Collision detection cost grows with droppable count (1000+ pages).
  - **`@atlaskit/pragmatic-drag-and-drop 4.0.0`** (2026-09-24, Apache-2.0, Atlassian): headless, native HTML5 DnD (so cross-window/cross-document and OS file drops work with the same primitives), framework-agnostic, tiny core, you own collision/hit-testing (cheap with a virtualized grid). 3.0/4.0 only changed entry-point paths. **Recommended** for multi-document page reordering; add its `hitbox` + `auto-scroll` addons and a custom keyboard fallback (it has no built-in a11y keyboard mode — you must implement move-with-arrows + live region).
  - `sortablejs 1.15.7` (2026-02) — DOM-mutating, poor fit with virtualized lists.
- **Worker RPC:** `comlink 4.4.2` (last release 2024-11-07; Proxy-based, ~1 kB, still the de-facto standard; transferables via `Comlink.transfer`). Alternatives if you want active maintenance: hand-rolled `MessageChannel` request/response with an id map (Evolu's "You might not need Comlink"), `kkrpc`, `minlink`. Comlink is fine; wrap it behind your own `PdfEngine` interface so it's swappable.

### Build tool: Vite 8
- **`vite@8.3.1`** (2026-09-24; 8.0 released 2026-03-12): Rolldown replaces esbuild+Rollup, Oxc transforms/minifier, Lightning CSS; Node ≥ 20.19/22.12; default `build.target` now Chrome 111/Edge 111/Firefox 114/Safari 16.4 (Baseline 2026-01-01), which conveniently includes module workers everywhere. - **WASM:** built-in `import init from './x.wasm?init'` (returns instantiate fn) or `'./x.wasm?url'` + `WebAssembly.instantiateStreaming(fetch(url))` (best for Emscripten glue, which wants a `locateFile`/`wasmUrl`); direct `import {fn} from './x.wasm'` needs top-level await support in the target. - **TypeScript 7.0.2** (2026-07-08; native Go compiler, ~10× faster `tsc`) — Vite uses Oxc for transpile, so use `tsc --noEmit` (tsgo) only for type-checking in CI.

## 7. Internationalization & accessibility

### i18n for a static app
- **Compiler-based (recommended): [Paraglide JS `@inlang/paraglide-js` 2.25.4](https://github.com/opral/paraglide-js)** (MIT): messages compile to typed, tree-shakable ESM functions; Vite plugin; ICU MessageFormat/i18next/JSON formats via plugins; works with React/Svelte/Solid/vanilla. Ships all used messages for all locales in one bundle by default — fine under ~20 locales (their benchmark), and per-locale lazy loading is possible by splitting the compiled output per locale and `import()`ing.
- **Runtime alternative: `i18next 26.4.2` + `react-i18next 17.0.15`** with `i18next-resources-to-backend` + `import(\`./locales/${lng}/${ns}.json\`)` for Vite code-split, lazy-loaded namespaces; larger runtime (~200–400 KB in benchmarks) but the richest ecosystem (plurals, contexts, ICU via plugin, translation-platform integrations).
- **Lingui `@lingui/core 6.8.0`** (macro-based, compiled catalogs) and `@formatjs/intl 6.1.2` are solid middle grounds.
- Regardless of library: use `Intl.NumberFormat`/`DateTimeFormat`/`PluralRules`/`RelativeTimeFormat` (all Baseline); detect locale from `navigator.languages` with a `?lang=`/hash override and persist in `localStorage`; RTL via `dir="rtl"` + CSS logical properties; keep locale files out of the precache except the active one.

### Accessibility for a canvas-based editor
- **Canvas is opaque to AT.** Keep the *semantic model in the DOM*: the thumbnail grid as a `role="grid"`/`listbox` of focusable items with `aria-selected`, `aria-rowindex`/`aria-colindex` for virtualized positions, and the page canvas as `role="img"` with `aria-label="Page 3 of 12, rotated 90°"`; expose text content via the pdf.js text layer (or engine text extraction) as an offscreen/readable DOM layer. Use `<canvas>` fallback content for the static description. (HTML spec canvas best practices; [APG patterns](https://www.w3.org/WAI/ARIA/apg/patterns/).)
- **Keyboard:** roving `tabindex` inside the toolbar (`role="toolbar"`, arrow keys) and the thumbnail grid (arrows/Home/End/PageUp/PageDown); `Space` to select, `Enter` to open, `Delete` to remove, `Ctrl/Cmd+Arrow` or `Alt+Arrow` to move pages (the DnD keyboard fallback pragmatic-dnd lacks), `R`/`Shift+R` rotate, `Esc` cancels drags; visible focus ring ≥ 3:1 (WCAG 2.2 SC 2.4.11/2.4.13), no keyboard traps (2.1.2), target size ≥ 24×24 (2.5.8). Avoid `role="application"` except on the freeform canvas region, and even then document the key map.
- **Announcements:** `aria-live="polite"` region for "Page 4 moved to position 2 in Document B", progress of long operations, and save completion; `aria-busy` on the grid while rendering.
- **Motion & vision:** honor `prefers-reduced-motion` (disable drag animations/zoom transitions; WCAG technique SCR40/C39), `prefers-color-scheme`, `prefers-contrast`; don't rely on colour alone for selection; zoom/contrast controls for rendered pages; ensure pinch/scroll zoom on canvas doesn't block page zoom (SC 1.4.4/1.4.10).
- **Testing:** `@axe-core/playwright` in E2E, `eslint-plugin-jsx-a11y`, manual NVDA/VoiceOver passes on the grid and toolbar.

## Bottom-line recommendations
1. **Ship single-threaded WASM engines in Web Workers (EmbedPDF/PDFium or pdf.js; avoid MuPDF's AGPL); do not depend on SharedArrayBuffer.** Offer `coi-serviceworker` later only as an opt-in enhancement with a "preparing…" reload screen; Safari needs `require-corp` and thus CORP headers on every third-party asset.
2. **File I/O tiering:** File System Access (Chromium) → OPFS + `<a download>` (Firefox/Safari) → plain `<input>`. Use OPFS as scratch; budget ~1 GB/document; stream saves.
3. **GitHub Pages:** custom Actions deploy (`upload-pages-artifact@v3` + `deploy-pages@v4`), `base: '/<repo>/'` propagated to router/PWA/SW/`wasmUrl`, hash routing (skip the 404 hack), accept 10-min `Cache-Control`, keep any single asset < 100 MB and the site ≪ 1 GB, prefer a custom domain to avoid shared-origin storage/SW clashes.
4. **PWA:** vite-plugin-pwa 1.3 today (migrate to `@vite-pwa/core` when stable), runtime-cache the big `.wasm`, `registerType: 'prompt'`.
5. **Stack:** Vite 8 + TypeScript 7 + React 19.3 (or Svelte 5) + Zustand/Jotai + TanStack Virtual + pragmatic-drag-and-drop 4 + Comlink; Vitest 5 (browser mode) + Playwright 1.63 screenshots in Docker; ESLint 10 + typescript-eslint 8 + Biome/Prettier; lefthook + commitlint; Changesets 3; Renovate; Lighthouse CI.
6. **i18n:** Paraglide JS 2 (compiled, typed) with per-locale lazy chunks; **a11y:** DOM semantics beside the canvas, roving tabindex, live regions, reduced-motion.
